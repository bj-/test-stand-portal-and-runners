# Сводки тестирования

Сводка отвечает на вопрос «Что мы проверили и достаточно ли доказательств для следующего шага?». Она фиксирует состояние модуля или проекта на дату. Отчет прогона, Allure и «Статистика» остаются отдельными источниками фактов о выполнении.

На «Обзоре» выберите проект и откройте последнюю сводку или «Все сводки». В разделе «Сводки» можно сменить проект, открыть прошлый срез, скачать Markdown и, если она опубликована, автономную HTML-презентацию.

## Как собрать сводку для любого проекта

1. **Зафиксируйте границы и версии.** Укажите проект, модуль, дату среза, версию и SHA продукта, SHA тестов, контракт, стенд и даты прогонов. Если источники относятся к разным версиям, покажите их отдельно. Не выдавайте старый прогон за результат текущей сборки.
2. **Посчитайте поверхность продукта.** Для API считайте уникальные пары «HTTP-метод + канонический путь». Сверьте контракт и реализации на выбранной версии. Health, документацию и служебные операции показывайте отдельно. Для UI, CLI или обработки данных единицей может быть поток, команда или сценарий. Назовите единицу в заголовке таблицы и объясните, что не вошло в знаменатель.
3. **Пересчитайте фактический каталог.** Исключите справочные примеры и заготовки, отдельно покажите setup, пропуски, ручные/неполные проверки и параметризованные варианты. Для API на каждую операцию дайте количество тестов по назначению и, если оно отличается, количество точных главных запросов. Один тест может покрывать несколько операций. Такие назначения нельзя складывать как число уникальных тестов.
4. **Опишите направленность.** Покажите позитивные и негативные случаи, контракт и валидацию, бизнес-логику, сквозные цепочки, доступ, данные и релевантные нефункциональные проверки. За основу берите метаданные или воспроизводимые правила классификации. Отделите непересекающиеся группы от меток, которые могут пересекаться. Приведите 1–2 характерных проверки на область. HTTP 2xx не равен автоматически позитивному бизнес-сценарию.
5. **Разведите три вида доказательств.** Покрытие операций, требований, сценариев, статусов или схем относится к дизайну тестов и требует явного знаменателя. Результаты выполнения берите из манифестов, JUnit, Allure или эквивалента и показывайте pass, fail, error, skip, проверки без assertions и проваленный gate. Покрытие кода берите из артефакта Jest/LCOV, Cobertura или аналога для нужного SHA. Укажите строки, ветви, функции и инструкции, если инструмент их измеряет. Для unit и e2e покажите отдельные охваты файлов, не усредняйте проценты. Если знаменатель или артефакт отсутствует, используйте «не измерено» или «не подтверждено», а не 0%.
6. **Оцените достаточность для решения.** Отдельно оцените ширину, глубину, воспроизводимость, подмены зависимостей и пробелы данных. Назовите, для чего тестов достаточно, а для чего нет. Падения не приравнивайте к дефектам. Укажите следующие действия, порядок и наблюдаемое условие, по которому будет понятно, что риск закрыт.
7. **Проверьте два артефакта.** В Markdown сохраните краткий вывод, таблицу покрытия, направления, прогоны, оценку и ссылки на версии источников. Для презентации возьмите из того же среза вывод, карту покрытия, профиль тестов, результаты, ограничения и действия. Встройте стили, скрипты и необходимые изображения в один HTML. Проверьте совпадение чисел, навигацию, мобильную ширину и открытие по `file://` без сети.

Минимальная таблица для API выглядит так.

| Метод и путь | Тестов по назначению | Главных запросов | Проверенные варианты / всего | Что проверяется и чего не хватает |
|---|---:|---:|---:|---|
| `GET /api/items` | 8 | 11 | 3/5 | Список, пустой ответ и валидация параметров. Не проверены два ответа из контракта |

## Как опубликовать в Test Portal

Положите комплект в настроенный клон результатов проекта в `summaries/<id>/`. Если клона нет или сводка хранится вне Git, оператор установки может положить ее в `PORTAL_ARTIFACTS/project-summaries/<код-проекта>/<id>/`. Допустимы два источника, но для одинакового ID приоритет у клона результатов. Код проекта берется из реестра Portal.

```text
summaries/2026-11-27-checkout/
  report.md
  slides.html
  summary.json
```

Пример манифеста в UTF-8.

```json
{
  "schema_version": 1,
  "title": "Checkout API — тесты и покрытие",
  "date": "2026-11-27",
  "module": "Checkout",
  "description": "Срез по контракту и двум прогонам. Пробелы и критерии приемки в сводке."
}
```

- В ID используйте строчные латинские буквы, цифры и дефисы. До 80 символов, первым идет буква или цифра. Для новой даты используйте новый ID, чтобы сохранить историю.
- `summary.json` и непустой `report.md` обязательны. `module`, `description` и `slides.html` можно опустить. `date` задается в формате `YYYY-MM-DD`. Допустимый размер манифеста до 16 КиБ, Markdown до 2 МиБ. Относительную ссылку `slides.html` внутри Markdown Portal заменяет ссылкой на скачивание.
- Публикуйте сводку после проверки права читателей на ее содержимое. Доступ к сводкам соответствует просмотру прогонов в установке, в том числе для гостя. Не переносите туда секреты, закрытые детали и сырые запросы. HTML скачивается отдельным файлом и не исполняется страницей Portal.
- Сводка появится после доставки файлов в хранилище установки и обновления страницы. Для нее не нужно запускать новый тест или импортировать прогоны. Старые папки архивных отчетов без манифеста остаются как есть.
