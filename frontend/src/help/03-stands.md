# Стенды

Стенд - развёрнутая версия тестируемой системы, на которой идут прогоны. Портал не знает, как стенд устроен: что
делает каждое действие, описано в конфигурации установки, выполняет его агент на сервере стендов.

## Создать стенд из шаблона

Кнопка **«Создать стенд»** доступна администратору, тестировщику и разработчику.
Мастер состоит из четырёх шагов:

1. Выберите проект и шаблон сборки. Шаблон задаёт компоненты, запуск и проверки стенда.
   Мастер предлагает рекомендуемую версию. Откройте выбор версии, чтобы повторить
   прежнюю конфигурацию. Портал подставляет имя из проекта, репозиториев и веток.
2. Выберите хост и исходники для настраиваемых компонентов. Подсказки предлагают ветки и теги.
   Можно ввести точный SHA. Для одинаковых имён ветки и тега используйте явную подсказку.
   Общую ветку можно применить к настраиваемым компонентам, в репозиториях которых она есть.
   Технические компоненты находятся внизу и по умолчанию свёрнуты. Разверните карточку,
   чтобы посмотреть репозиторий и ревизию из шаблона.
3. Выберите профиль ресурсов, параметры, окружения и срок использования.
   Разработчику доступны временные стенды. Дата окончания пока сохраняется как
   настройка: автоматическая остановка по сроку появится отдельно.
4. Проверьте имя и сводку, нажмите **«Проверить конфигурацию»**, затем **«Создать стенд»**.

Предложенное имя обновляется при выборе исходников. Ручной ввод сохраняется.
Если в проекте уже есть стенд с таким именем, измените его или подтвердите дубль.
Портал предложит добавить логин в скобках и подберёт порядковый номер при повторном совпадении.

В каталоге проекта администратор может открыть **«Компоненты мастера»** у нужной
версии шаблона. Отметка **«Технический»** фиксирует источник для сборки и исключает
его ветку из предложенного имени. Для настраиваемых компонентов имя учитывает
отметку **«Ветка в имени»**.

Ошибка проверки или конфликт порта сохраняют заполненные поля. После изменения
настроек нужна новая проверка. Порты в сводке предварительные: они резервируются
при создании. Отсутствие агента не мешает создать стенд — сборка будет ждать его.

Если сервер мог принять запрос, но ответ потерян, используйте **«Повторить исходный
запрос»**. Эта кнопка проверяет результат прежней операции и не создаёт второй стенд.
Не начинайте новый запрос, пока не выяснен результат предыдущего.

После создания откроется **«Сборки и состояние»**: здесь видны этапы, выбранные
версии исходников, история, журнал задачи и отчёты Allure. **«Повторить по этим SHA»**
использует сохранённые версии, сохраняет данные стенда и предыдущие результаты.
Отмена доступна в журнале задачи; она не удаляет экземпляр и его данные.

В **«Сборки и состояние»** администратор или создатель может нажать
**«Удалить стенд»** и подтвердить очистку. Исполнитель удалит контейнеры,
тома и данные этого экземпляра. После успешной очистки освободятся порты, а
история сборок и Allure останутся доступны по прежней ссылке.
Подписи адресов из шаблона видны в мастере и на карточке стенда.

Если проекта или шаблона ещё нет, администратор может создать проект и открыть
**«Каталог проекта»**, зарегистрировать совместимые репозитории и нажать
**«Добавить шаблон»**. В диалоге загрузите JSON-файл portable v1, проверьте
компоненты и ресурсы и зарегистрируйте версию. Для изменения сохранённого шаблона
подготовьте новую версию. Локальные копии
репозиториев и доступ к ним заранее настраивает администратор установки на хосте.

В разделе **«Шаблоны стендов»** можно скачать учебный JSON и скопировать промпт
с ключами репозиториев проекта. Передайте промпт LLM вместе с Compose, Dockerfile
и инструкциями по сборке и проверке приложения. Перед регистрацией проверьте
результат по исходникам, затем выполните пробное развёртывание.
Конфигурации пересборки действующих стендов показывают значения ревизий
из манифеста установки. Мастер создания использует зарегистрированные версии portable v1.

В разделе **«Git-серверы»** нажмите **«Добавить сервер»**. Для выбора из списка
сохраните токен с доступом к API. В таблице видны наличие токена и права для выбранного режима.
Чтобы заменить или удалить токен, нажмите **«Изменить»** у подключения. Для
разных токенов можно добавить несколько подключений к одному Git-серверу.

В разделе **«Репозитории»** нажмите **«Добавить репозиторий»** и выберите
Git-сервер. Кнопка **«Добавить сюда»** в его группе сразу подставляет сервер в
форму. Введите `группа/репозиторий` или полный HTTPS URL без токена в URL.
При наличии токена API для GitLab или GitHub рядом появится список. Выбор из
списка подставляет URL в то же поле.
После проверки URL форма покажет **отображаемое название**, **ключ для шаблонов**
и **компоненты стенда**. Название можно изменить. Портал назначает постоянный
ключ автоматически и учитывает группу, если такое имя уже занято. Компоненты
берутся из зарегистрированных шаблонов проекта, которые ссылаются на этот ключ.
Список компонентов можно исправить или заполнить вручную. Сборка использует
Git-репозитории, настроенные на хосте исполнителя.

- **GitLab, список.** Нужен проектный, групповой или личный access token с
  `read_api`.
- **GitHub.** Fine-grained personal access token для выбранных репозиториев
  с правом `Metadata: read` для списка.

## Карточка стенда

Стенды сгруппированы по проектам. Нажмите заголовок проекта или стенда, чтобы
свернуть или раскрыть его. Портал запоминает раскрытие в этом браузере отдельно
для каждого пользователя; у гостя своё состояние. В свёрнутой карточке остаются
название, состояние и признак занятости. Кнопка «Обновить» сохраняет раскрытие.

- **Описание** - ветки, учётные данные для входа, особенности стенда.
- **Известная проблема** - если записана, стенд помечен нерабочим, пока её не уберут из конфигурации.
- **Адреса** - ссылки на сервисы стенда (Swagger, почтовый ящик и т. п.).
- **Доступы** - адреса и пароли баз. Видят только тестировщики, разработчики и администраторы; пароли скрыты до
  нажатия «показать», значения можно скопировать.
- **Что на стенде** - когда собран и развёрнут; по каждому компоненту ветка, коммит, **срез** (время коммита - на какой
  момент собран код), версия пакета и версия API; сколько миграций применено.
- **Окружения тестов и последние прогоны** - какие окружения тестов смотрят на этот стенд и чем закончился последний
  прогон на каждом.
- **Проверка стенда** - список проверок с итогами (раскрывается).

## Состояние: работает / не работает / не проверен

**Не работает** (красная рамка и плашка), если верно хоть одно:

- записана известная проблема;
- не прошла проверка стенда: контейнер не запущен, API не отвечает, применены не все миграции, хранилище не пишет данные;
- после последнего развёртывания прогон не прошёл **gate** (короткий смоук в начале каждого прогона) или упал смоук.

**Работает** - проверка стенда прошла и после развёртывания был успешный прогон.
**Не проверен** - нет проверки или после развёртывания ещё не было прогона.

Проверка стенда выполняется после каждого развёртывания и автоматически каждые несколько минут.

## Действия

| Действие | Что делает | Кто может |
|---|---|---|
| Пересобрать и развернуть | Собрать образы из указанных веток или коммитов, накатить миграции, перезапустить | тестировщик, администратор |
| Перезапустить | Поднять все сервисы стенда без пересборки | тестировщик, администратор |
| Тестовые данные | Открыть состав тестовых данных без запуска задач | роли с правом просмотра тестовых данных стенда |
| Засеять тестовые данные | Выполнить засев из конфигурации и применить подключённые наборы | тестировщик, администратор |
| Сбросить данные | Удалить все данные стенда и развернуть заново (с засевом, если он описан). Только с подтверждением | тестировщик, администратор |
| Состояние | Обновить проверку, показать ревизии и контейнеры | разработчик, тестировщик, администратор |
| Логи | Последние строки логов приложений | разработчик, тестировщик, администратор |

- **Подтверждение базовых действий.** Пересборка, перезапуск, засев и сброс открывают окно: что будет сделано и чем это грозит. Запуск -
  только после отметки «Понимаю, что произойдёт»; для сброса данных нужно ещё ввести название стенда.
- **Тестовые данные** открывает диалог с базовым составом данных, описанным в конфигурации установки, и каталогом наборов проекта.
  Просмотр доступен независимо от наличия команды засева и ничего не меняет на стенде.
- **Засеять** и **Сбросить данные** находятся внутри этого диалога и видны только тестировщику и администратору,
  если соответствующая команда описана у стенда. Запуск требует подтверждения; сброс удаляет **ВСЕ данные стенда**.
- «Состояние» и «Логи» ничего не меняют и запускаются сразу.
- Действие становится задачей в очереди; после подтверждения открывается её живой лог.
- **Стенд занят**, пока на нём идёт прогон или пересборка: следующие такие задачи ждут. «Состояние» и «Логи» не ждут.
- После пересборки, перезапуска и сброса портал сам запускает **смоук** - нерабочая сборка сразу видна на карточке.

## Наборы тестовых данных

Наборы общие для проекта и хранятся в неизменяемых версиях. Их можно применить сразу или подключить к стенду для автоприменения. Инструкция по созданию, выбору версии и цели и пример JSON — в разделе [Наборы тестовых данных](#test-datasets).

При развёртывании, засеве и сбросе включённые подключения с автоприменением выполняются после базовой команды. При развёртывании и сбросе они выполняются до смоука; сам засев смоук не запускает. Версии фиксируются при постановке задачи в очередь. Ошибка применения останавливает цепочку; уже сделанные изменения других целей могут сохраниться.
