# Доступ агента к репозиториям

Начиная с версии **0.2.0** агент Newman требует HTTPS API библиотеки и клиентский ключ.
Используйте движок **0.12.0** или совместимую более новую версию.

| Переменная | Значение |
| --- | --- |
| `AUTOTEST_LIBRARY_API_URL` | Корень HTTPS API, без учётных данных, query и fragment |
| `AUTOTEST_LIBRARY_API_KEY_FILE` | Абсолютный путь к закрытому bearer-ключу, доступному UID раннера |
| `AUTOTEST_LIBRARY_API_KEY` | Ключ из защищенного окружения службы вместо файла |

Файл ключа монтируется отдельно read-only в `/run/secrets/library-api-key`; при использовании
окружения значение передаётся Docker через имя переменной, без значения в argv и логе.
Ключу нужны scopes `checks:runner` и `runner:resources`. `AGENT_TOKEN` не используется для библиотеки.
Агент получает проверки и ресурсы через API. Ошибка API останавливает прогон.
URL и наличие ключа проверяются для каждого задания Newman до Git-операций.
Ошибка конфигурации завершает задание со статусом `failed`; агент продолжает работу с очередью.

При обновлении с 0.1.x задайте `AUTOTEST_LIBRARY_API_URL` и
`AUTOTEST_LIBRARY_API_KEY_FILE`, обеспечьте доступ UID раннера к файлу и перезапустите
агента. Файл имеет приоритет над `AUTOTEST_LIBRARY_API_KEY`.
`AGENT_LIBRARY_URL` больше не поддерживается. Удалите эту настройку и отдельный
GitHub-токен библиотеки из конфигурации службы. GitLab-токен остается нужен для
репозиториев тестов и результатов. Существующий клон Test-Library больше не используется.

Ключ библиотеки нужен только заданиям Newman. Прогоны pytest и задачи stand-host
выполняются без него. Настройки API библиотеки не передаются процессам pytest
и адаптерам данных.

## Демонстрационная установка с локальными результатами

По умолчанию `AGENT_GIT_MODE=remote`: агент обновляет репозитории и публикует результаты как раньше.
Для отдельной демонстрационной установки задайте `AGENT_GIT_MODE=local-results`:

| Переменная | Значение |
| --- | --- |
| `AGENT_GIT_MODE` | `local-results`: результаты только в локальной ветке `main`, без fetch/pull/push и без reset/clean клона результатов |
| `AGENT_GIT_TIMEOUT` | Положительное число секунд для clone/fetch в этом режиме, по умолчанию `15` |
| `AGENT_WORK` | Отдельный каталог установки с `<PROJECT>/tests` и `<PROJECT>/results`; не пользовательские рабочие копии |
| `AGENT_TESTS_OVERLAY_DIR` | Необязательный каталог overrides: `<dir>/<PROJECT>/.local/*.yaml` |
| `AFTER_JOB` | Команда индексации именно локального `<AGENT_WORK>/<PROJECT>/results` |

Origins сохраняются. Для тестов агент пробует fetch; при ошибке или timeout использует существующий
кэш, выводит commit в лог и проверяет выбранный `origin/<ref>`. Отсутствующая ветка остаётся ошибкой.
Заранее перенесите обычные клоны с нужными refs; без кэша первый clone должен завершиться успешно.
Локальная ветка результатов `main` сохраняет предыдущие прогоны, включая ignored raw/Allure.
Агент отклоняет незакоммиченные изменения вне `runs/` и `history/<модуль>/allure-history.jsonl`;
используйте один агент этой установки.
Результаты коммитятся локально, Allure загружается в портал, выполняется `AFTER_JOB`.
Автоматической последующей публикации этих демонстрационных коммитов нет.

Для индексации задайте `projects.yaml` поле `results` на этот checkout (путь внутри контейнера портала)
и смонтируйте его read-only. Поле `tests` указывает на отдельную рабочую копию с каталогом наборов и refs.
`tests_url` и `results_url` сохраняют исходные адреса. `AFTER_JOB` должен вызывать `portal.cli sync`,
не обёртку, которая перед этим требует успешный Git pull. Library API и его ключи остаются настроены
обычным способом; этот режим не меняет механизм доступа к библиотеке.

После checkout/clean тестов агент копирует только плоские `.local/*.yaml` из overlay.
Это штатный механизм движка: имя `<точное имя окружения>.yaml`, содержимое — YAML map, например
`baseUrl: http://127.0.0.1:3102`. Выбирайте существующее имя окружения из `environments` установки;
overlay меняет его значения, но не создаёт новый базовый environment или набор.
В `.local` можно задать остальные адреса и тестовые учётки этой установки.
Каталог `.local` должен быть ignored в репозитории тестов. Символические ссылки, junctions,
выход за каталог проекта и перезапись tracked файлов отклоняются. Файлы копируются только в
приватный checkout агента; пользовательские исходные клоны не изменяются.

## Обычный Newman-прогон на переносимом стенде

Для управляемых прогонов задайте `AGENT_MANAGED_STAND_HOST=<host-id>` и оставьте
`newman` и возможность проекта в `AGENT_CAPABILITIES`. Агент добавит
`managed-newman-v1` и передаст `host_id` при запросе задания. Привяжите ключ
этого агента к тому же хосту в настройках установки.

Портал передаёт ID экземпляра в `stand`, идентификатор окружения в `env` и адреса
готовой сборки в `stand_target`.

```json
{"host_id":"local-host","binding":"apiUrl","build_id":"build-7","bindings":{"apiUrl":"http://127.0.0.1:3102/api","authUrl":"http://127.0.0.1:3103"}}
```

`binding` содержит ключ из `bindings`. Агент проверяет совпадение хоста и адреса
HTTP(S). Каждый ключ становится переменной окружения Newman. Выбранная привязка
задаёт `baseUrl` без завершающего `/`, чтобы набор мог добавить путь запроса.
Агент формирует окружение на время прогона. Действуют фильтры
наборов, gate и точный выбор `test_ids`. Отчёты создаются с `--secrets mask`.

Тестовые учётки и другие параметры можно задать в плоском YAML-файле
`<AGENT_TESTS_OVERLAY_DIR>/<PROJECT>/.local/<env>.yaml`. Для экземпляра `stand-1`
и привязки `apiUrl` имя файла будет `stand-1--apiUrl.yaml`. Дочерний процесс
читает файл и применяет поверх него адреса сборки. Если установка не указала
`safeFailedLogins`, движок получает порог 1. Храните файл вне Git с доступом
у службы агента.

Для Docker Desktop можно задать
`AGENT_MANAGED_STAND_LOOPBACK_HOST=host.docker.internal`. Агент подставляет это
доверенное имя в опубликованные loopback-адреса сборки. Схема, порт, путь и
параметры сохраняются. HTTPS требует доверенного сертификата для имени или IP,
по которому исполнитель подключается к сервису. Допуск сборки, очередь и
привязку ключа к хосту проверяет API портала.

При создании стенда с комплектом исполнитель может подготовить файл окружения
выбранного сервиса в том же каталоге overlay. В такой файл адаптер может записать
публичный PEM-сертификат через служебное поле `__portal_ca_pem`. Дочерний процесс
добавляет его к системному доверию для запроса OpenAPI и Newman. Доверие действует
в одном прогоне, имя или IP продолжают проверяться по сертификату.

# Адаптер тестовых данных relational-v1

`data_adapter.py` — отдельная команда Python 3.12 для существующих SQLite и PostgreSQL БД стенда. SQLite использует стандартную библиотеку, но библиотека SQLite должна поддерживать `RETURNING` (3.35+). Только для PostgreSQL установите `psycopg` версии 3 в окружение этой команды, например `pip install 'psycopg[binary]>=3,<4'`. Импорт psycopg выполняется только при выборе postgres.

Включение требует установки файла на stand-host и настройки `test_data` в manifest. Наличие исходника в репозитории само по себе ничего на стенде не включает. Деплой здесь не выполняется. Полный сценарий портала и API: [docs/test-data.md](../docs/test-data.md).

## Конфигурация установки

| Переменная | Значение |
| --- | --- |
| `PORTAL_DATA_DRIVER` | `sqlite` (по умолчанию) или `postgres` |
| `PORTAL_DATA_SQLITE_PATH` | Путь к существующему файлу БД, только из окружения установки |
| `PORTAL_DATA_POSTGRES_DSN` | DSN PostgreSQL, только из окружения установки |
| `PORTAL_DATA_SCHEMA` | Схема по умолчанию: `main` для SQLite, `public` для PostgreSQL |
| `PORTAL_DATA_ALLOWED_SCHEMAS` | Необязательный список схем через запятую, например `public,fixtures` |
| `PORTAL_DATA_ALLOWED_TABLES` | Необязательный список полных имён, например `public.users,public.orders` |

Без allowlist доступны поддерживаемые таблицы, на которые у учётной записи БД есть права. Пустая явно заданная allowlist запрещает всё. Для установки рекомендуется явный список и отдельная учётная запись с минимальными правами. SQLite ограничен `main`: нет ATTACH, временных и виртуальных таблиц. Секреты передаёт защищённое окружение процесса или доверенная обёртка установки; `secrets_files`, показывающие доступ к стенду в UI, сами по себе не являются настройкой подключения адаптера.

Пример доверенной команды manifest:

```yaml
test_data:
  primary:
    title: Основная база
    format: relational-v1
    apply: /opt/stand/bin/primary-data
    inspect: /opt/stand/bin/primary-data
    timeout: 120
```

Обёртка `primary-data` читает защищённую конфигурацию установки, экспортирует перечисленные переменные и выполняет `exec python3 /opt/test-portal/agent/data_adapter.py`. Обёртка для второй цели/стенда задаёт другое подключение. Она не выбирает путь или DSN из пользовательского JSON. Портал проверяет проект/стенд/цель, сам адаптер использует ровно подключение своей команды.

## Файловый протокол

Агент запускает команду в `stand.workdir`. `PORTAL_DATA_INPUT` и `PORTAL_DATA_OUTPUT` содержат пути файлов в закрытом временном каталоге агента (0700, файлы 0600 на POSIX). Полезная нагрузка не передаётся через argv или переменные окружения. Размер `data`/`query` ограничен **2 MiB UTF-8** в компактной JSON-сериализации; весь входной файл допускает дополнительно 64 KiB для envelope:

```json
{"protocol":1,"operation":"apply","project":"ACME","stand":"dev","target":"primary","format":"relational-v1","data":{"tables":[{"table":"users","key":["id"],"rows":[{"id":-101,"name":"Example"}]}]},"query":null,"dataset":{"id":1,"version":1}}
```

Для inspect `data` и `dataset` равны null, `query` содержит запрос ниже. Все поля envelope обязательны. Неизвестные поля, повторяющиеся JSON-ключи, NaN/Infinity запрещены. Выход — JSON object до 2 MiB в `PORTAL_DATA_OUTPUT`; stdout/stderr не используются. Успех: код завершения 0 и `ok:true`; ошибка: код 1 и `{"ok":false,"error":{"code":"..."}}`. Не публикуйте файл результата в общих логах: inspect содержит фактические данные. Агент ограничивает время и отменяет группу процессов; адаптер не запускает дочерние процессы.

## Применение

```json
{"tables":[
  {"table":"public.users","key":["id"],"rows":[{"id":-101,"name":"Example","active":true}]},
  {"table":"public.orders","key":["id"],"rows":[{"id":-201,"user_id":-101,"total":12.5}]}
]}
```

Для SQLite используйте `main.users` или `users`. Нужны существующие таблицы, колонки и обычный PRIMARY KEY либо полный уникальный индекс по `key`. Partial/expression индексы и PostgreSQL deferrable unique ограничения не подходят. Имена состоят из ASCII букв, цифр и `_`, начинаются с буквы/`_`, длина до 63; имя таблицы — `table` или `schema.table`. Имена экранируются, значения параметризуются.

Входные значения — только JSON-скаляры: строки без NUL, bool, null, конечные числа; целые в диапазоне signed 64-bit. Типы и ограничения дополнительно проверяет БД. JSON/array/bytea значения на запись не поддерживаются; даты, UUID и decimal можно передать строкой, если тип целевой колонки допускает такое преобразование. Generated и PostgreSQL GENERATED ALWAYS AS IDENTITY колонки не записываются; BY DEFAULT AS IDENTITY поддерживается. Sequence serial/identity не перенастраивается: фиксированные ID набора должны исключать столкновение с будущими авто-ID (например отрицательные ID при положительной sequence или отдельный естественный ключ). Заданные ключи обязательны и не могут содержать null. Пустые tables/rows, повтор одной таблицы и повтор ключа в rows — ошибка. Дубликаты проверяются также по возвращённым БД ключам после преобразований типов и collation; ошибка откатывает всю транзакцию.

Одна транзакция охватывает все таблицы в порядке массива: сначала родители, затем дочерние записи. Upsert обновляет только переданные неключевые колонки; отсутствующие колонки сохраняются при обновлении и используют default при вставке. Только ключи означают вставку либо сохранение существующей строки. Лишние строки не удаляются. Нет DDL, raw SQL, файловых путей или DSN в payload. Результат содержит количество обработанных строк, а не число реально изменённых строк:

```json
{"ok":true,"operation":"apply","tables":[{"table":"public.users","rows":1}],"rows":1}
```

Повтор восстанавливает те же переданные значения. Триггеры БД могут иметь собственные побочные эффекты и нарушать эту идемпотентность: для fixture-таблиц их должен оценить владелец БД. Внешние побочные эффекты триггеров транзакция адаптера отменить не может. SQLite включает foreign_keys; PostgreSQL использует ограничения самой БД.

## Просмотр

```json
{"table":"users","where":{"id":-101,"deleted_at":null},"columns":["id","name"],"limit":100}
```

`where` обязателен; `{}` разрешает просмотр первых строк. Только равенство через AND; null превращается в `IS NULL`. Нет выражений, сортировок, JOIN, операторов сравнения или SQL. `columns` по умолчанию — все колонки; `limit` — целое 1–1000, по умолчанию 100. Порядок строк не определён. `truncated:true` означает наличие ещё хотя бы одной строки за limit. Запрос работает в read-only транзакции. Переполнение 2 MiB возвращает ошибку без частичного результата; уменьшите limit/columns.

Выходные decimal — строки (включая точность), даты/время — ISO-строки, UUID — строки, bytes — `{"encoding":"base64","value":"..."}`. JSON/array, возвращённые PostgreSQL, рекурсивно сериализуются. Неизвестные типы и нечисловые float/decimal дают `unsupported_result_type`.

Коды ошибок не включают данные или текст исключения: например `key_not_unique`, `duplicate_row_key`, `column_not_writable`, `table_not_allowed`, `result_too_large`, `postgres_driver_unavailable`. Ошибки подключения/SQL/ограничений намеренно объединены в `database_or_configuration_error`. Подробности диагностируйте на стороне БД с ограниченным доступом. При потере процесса/выходного файла после COMMIT результат может быть неопределённым для портала: проверьте inspect и повторите идемпотентное применение. Между БД стенда и БД портала нет распределённой транзакции.

Семантика UPSERT: [PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html), [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html).

## Другие хранилища

Универсален портал и его файловый протокол, а предоставленные драйверы покрывают SQLite/PostgreSQL. Для MongoDB, API, графовых структур или составных доменных объектов нужен собственный адаптер и отдельный стабильный `format` (например `mongo-documents-v1`). Он валидирует свой JSON, использует секреты установки, реализует apply/inspect, идемпотентность и доступные транзакционные гарантии. Нельзя выдавать произвольному JSON право задавать команду, DSN или адрес внешнего API. Портал не превращает relational-v1 в универсальный формат любой БД.
