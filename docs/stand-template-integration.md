2026-11-18. Переносимый контракт и CLI находятся в
`test-stand-portal-and-runners/stands/README.md`. Подготовлен воспроизводимый

Учебный шаблон и скрипт deploy выполняют миграцию/засев/healthcheck/smoke/Allure;

Регистрация через [API](stand-management-api.md) и исполнение `stand-build`

настоящими API/агентом; конфигурация существующих экземпляров пока не редактируется.

## Граница переносимого компонента

Шаблон задаёт компоненты, зависимости, Compose, последовательность стадий,
ресурсы, параметры, ссылки на секреты и привязки окружения. Каталог установки
сопоставляет разрешённые идентификаторы репозиториев с локальными clones.
Пользователь выбирает refs и объявленные параметры; команды и пути репозиториев
приходят из доверенной конфигурации установки.

`prepare` сохраняет полные SHA и копию шаблона, экспортирует committed files
в отдельные контексты. `replay` использует SHA и шаблон из снимка.
Незакоммиченные изменения исходного clone не входят в состав сборки.
Это фиксация исходников, а не гарантия воспроизводимости Docker-образа:
executor фиксирует ID полученных образов и доступные RepoDigests. Он не закрепляет
mutable base tags и зависимости сборки; registry digest локального образа может отсутствовать.

Standalone prepare разрешает refs по локальному каталогу Git. Worker поддерживает
явный `fetch: true`: ограниченный fetch origin, разрешение обновлённых remote refs
без checkout и без fallback при ошибке. Доступ Git задаётся на хосте. По умолчанию
fetch выключен, изменение ветки на сервере не обновляет локальный clone.

## Существующие точки интеграции

| Область | Текущий контракт портала и движка | Что нужно подключить дальше |
|---|---|---|
| Реестр | `load_registry(session)` объединяет YAML/БД; API проверяет контракт и атомарно создаёт экземпляр/порты/задание | Подключение исполнения и отдельный явный импорт прежних YAML-стендов |
| Выполнение | Старый `stand-host` выполняет Bash; новый `stands.worker` получает только `stand-template-v1` своего хоста | Продуктовый адаптер и расширение платформенной приёмки |
| Состав продукта | `StandConfig.info_file`: `components: [{name, commit, version?}]`; `product_on()` отдаёт коммиты прогону | Отображение каждого component ID и полного SHA снимка в `name` и `commit`; запись только после подтверждённого развёртывания |
| Запуск тестов | Агент передаёт `--build` и `--product-commit name=SHA`. Форма выбирает стенд и сервис | Настроить тестовые данные конкретного приложения |
| Smoke | `StandConfig.smoke`: `suite`, `env`, необязательный `ref`; очередь проверяет наличие неразрушающего набора | Smoke шаблона должен ссылаться на существующий набор и разрешённое окружение проекта |
| Адреса | В созданном стенде выбранная опубликованная привязка задаёт `baseUrl`. Агент может добавлять `.local/<env>.yaml` | Настроить маршрутизацию и доверие к HTTPS на хосте Newman |

Имя переменной `STAND_URL` не заменяет `baseUrl` для текущего newman runner.
Утверждение о текущем поведении основано на `test-engine/engine/run.py:load_env()`
и `test-portal/agent/agent.py:apply_tests_overlay()`.

Overlay агента расположен по адресу
`AGENT_TESTS_OVERLAY_DIR/<PROJECT>/.local/<env>.yaml`. Это плоская YAML map;
она переопределяет значения существующего окружения, но не создаёт базовое
окружение или набор тестов. Агент копирует её в свою рабочую копию тестов;
символические ссылки, junctions и перезапись tracked-файлов запрещены.
Секреты остаются в конфигурации установки, отдельно от переносимого снимка.

Адрес внутри Compose-сети и адрес хоста — разные значения. Привязка шаблона
описывает сервис и порт, но публикация порта и выбор адреса runner относятся
к исполняющему адаптеру. Текущий Linux runner использует `--network host`;
это не подтверждает переносимость агента на Docker Desktop.

## Оставшаяся приёмка D и E

1. Подключить адаптер целевого приложения; нейтральный шаблон уже принят на
   Docker Desktop Windows, с настоящими PostgreSQL/API/агентом и Allure.
2. Настроить для продуктовых сценариев учётки, тестовые данные и доверие к HTTPS
   по [инструкции агента](../agent/README.md).
3. Подключить изменение существующего экземпляра и явный импорт прежних YAML-стендов.
4. Проверить полный сценарий через локального агента на Windows/Ubuntu/macOS,
   сохранение результатов, backup/restore и откат миграции на отдельной копии.

Проверка CLI сама по себе не закрывает платформенную приёмку. Сквозной сценарий
принят через API и мастер в браузере на Windows; другие ОС ещё требуют проверки.
