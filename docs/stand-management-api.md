# Каталог и создание стендов через API

API используется для регистрации шаблонов и создания стендов из портала.
Нужна миграция до `0015`. Созданный экземпляр появляется в существующем реестре;
сборку выполняет [локальный агент](local-stand-agent.md), привязанный к выбранному
хосту. При его отсутствии причина ожидания видна в API и UI. Мастер доступен
через «Стенды → Создать стенд»; каталог проекта настраивает администратор.

## Каталог установки

`PORTAL_STAND_HOSTS` указывает на внешний JSON, доступный процессу портала:

```json
{
  "schema_version": 1,
  "hosts": [{
    "id": "laptop",
    "title": "Локальный стенд",
    "port_range": [20000, 20999],
    "repositories": {
      "DEMO": {"demo": "/data/mirrors/demo"}
    }
  }]
}
```

Для портала в Docker это путь **в контейнере**: файл и clone следует смонтировать
для чтения. Для нативного Windows-процесса допустим абсолютный Windows-путь.
Отсутствующая переменная означает пустой каталог; указанный, но недоступный файл —
ошибку. Указание хоста не запускает и не регистрирует агента.

Зеркало — существующий non-bare clone или worktree с нужными локальными ветками
и тегами. Его подготавливает и обновляет установка. Каталог выбранного хоста
определяет зеркало для проверки и сборки. На хосте исполнителя настройте его
собственный каталог репозиториев.

## Маршруты

Все новые маршруты требуют входа. Каталоги доступны пользовательским ролям;
изменение каталогов — администратору. Гость, `llm` и агент их не администрируют.

| Метод и путь после `/api` | Назначение |
|---|---|
| `POST /projects` | Новый проект БД: `{code,title,configuration}`; существующий код даёт 409 |
| `GET /stand-hosts` | ID, название и диапазон портов; без путей зеркал |
| `GET /git-servers` | Подключения Git для выбора администратором. Ответ содержит только состояние `has_token` и параметры подключения |
| `POST /git-servers` | Создание подключения `{title,base_url,provider}`. Для одного HTTPS-адреса можно создать несколько подключений с разными правами |
| `PATCH /git-servers/{id}` | Изменение названия `{title}` |
| `PUT /git-servers/{id}/token` | Сохранение или замена `{token,username?,access}`. `access` равен `git` или `api`, `token: null` удаляет токен |
| `GET /git-servers/{id}/repositories?page=1` | Страница из доступных токену репозиториев GitLab или GitHub `{items,page,has_next}` |
| `GET /projects/{code}/stand-repositories` | Разрешённые репозитории, их `git_url`, `git_server_id` и компоненты |
| `POST /projects/{code}/stand-repositories/preview` | Проверка HTTPS URL по выбранному серверу `{git_url,git_server_id}`. Возвращает предлагаемые ключ, название и компоненты без записи |
| `POST /projects/{code}/stand-repositories` | Создание `{git_url,components?,enabled,git_server_id?,key?,title?}`. При автоматическом получении ключа совпадение имён разрешается через путь группы. Повтор URL в том же подключении при автоматическом ключе или повтор явно заданного ключа даёт 409 |
| `PUT /projects/{code}/stand-repositories/{key}` | Изменение `{title,components,enabled,git_url?,git_server_id?}`. Пропущенные URL и подключение сохраняются |
| `GET /projects/{code}/stand-repositories/{key}/refs?host=laptop` | Локальные branches/tags: `{name,kind}` |
| `GET /projects/{code}/stand-templates` | Версии и сведения для выбора профиля/компонентов/параметров |
| `GET /projects/{code}/stand-deployment-configurations` | Для администратора. Стенды установки с действием пересборки и их значения параметров `*_REF` по умолчанию |
| `POST /projects/{code}/stand-templates` | `{title,spec}`; spec — полный portable v1. Идентичный повтор 200, изменение версии 409 |
| `PATCH /projects/{code}/stand-templates/{key}/{version}/naming` | Администратор задаёт `name_ref_exclusions` со списком ID компонентов, чьи ветки пропускаются в имени стенда. Возвращает проекцию шаблона |
| `PATCH /projects/{code}/stand-templates/{key}/{version}/wizard-settings` | Администратор сохраняет два списка ID компонентов `{name_ref_exclusions, technical_components}` для выбранной версии. Возвращает проекцию шаблона |
| `GET /projects/{code}/stand-instance-name?name=…` | Проверка имени для создателя с пользовательской сессией. Возвращает `{conflict: null}` или `{conflict: {name, stand_id, suggested_name}}` с доступным именем для дубля |
| `POST /projects/{code}/stand-instances/preflight` | Проверка запроса без записи и резервации |
| `POST /projects/{code}/stand-instances` | Атомарное создание; обязательный заголовок `Idempotency-Key` |
| `GET /projects/{code}/stand-instances/{id}` | Состояние, владелец, задание, порты и причина ожидания |
| `DELETE /projects/{code}/stand-instances/{id}` | Администратор или создатель ставит задачу на удаление. После очистки исполнитель подтверждает результат, портал освобождает имя и порты. История и Allure доступны по прежней ссылке |

Настройки `configuration` проекта: `results`, `tests` (абсолютные пути или null),
`tests_url`, `results_url`, `environments`, `runner`, `capability`.
Пустой объект создаёт проект без репозиториев тестов/результатов. Для YAML-проекта
повторный `POST /projects` не нужен: каталог можно регистрировать под его кодом.

При проверке имени учитываются ID и названия действующих стендов проекта.
Если подтверждённое имя заняли до создания, передайте его как `name`, а исходное
имя как `base_name`. Так портал предложит следующий номер для той же основы.
Проверка имени не резервирует его. `POST /stand-instances` проверяет имя повторно в транзакции.

Каталог версий возвращает `name_ref_exclusions` и `technical_components`. По умолчанию
оба списка пустые. Мастер пропускает в предложенном имени ревизии компонентов из
обоих списков. `PATCH .../naming` обновляет `name_ref_exclusions` независимо от
`technical_components`.

Предварительная проверка и создание стенда используют `repository` и `default_ref`
из portable v1 для каждого технического компонента. Запрос может передать эти же
значения или опустить их. Другой репозиторий или ревизия дают 422. Агент получает
весь состав и зависимости из спецификации и фиксирует SHA всех компонентов.

Шаблон и repository IDs должны соответствовать переносимому контракту.
Незаполненные компоненты при создании предлагаются по версиям шаблонов проекта,
которые ссылаются на ключ репозитория. Явный массив компонентов сохраняется как
задан, включая пустой массив. Параметры предварительного просмотра вычисляются
повторно при создании записи, чтобы учесть изменения каталога.
Git URL указывают без логина, пароля, параметров и фрагмента. Привязанный
репозиторий должен находиться на заданном HTTPS-адресе сервера, включая порт.
Запрос списка по API использует текущий токен подключения и выполняется без
переадресаций. Для ручного ввода достаточно пути или HTTPS URL..

Пример шаблона находится в `test-stand-portal-and-runners/examples/template-demo/template.json`.
Для него зарегистрируйте repository `demo` с `components: ["api", "smoke"]`
и подготовьте локальную ветку `test` в зеркале. Сам API исходники примера не создаёт.

У `output_bindings` можно указать `title` для каждого адреса. Портал передаёт
подписи в `output_binding_titles` каталога, preflight, экземпляра и сборки.

Портативный шаблон может включать `liveness`. Ключ объекта — сервис Compose из
одного из профилей, значение — команда `{component, argv}` с `docker compose run`.
Агент выполняет проверки отклика для активного профиля после ошибки smoke.
При подтверждённом отклике экземпляр получает `status: limited`, карточка —
`health.state: limited`. См. [протокол агента](local-stand-agent.md#протокол-и-результаты).

Каталог также показывает конфигурации пересборки, которые читает из манифеста установки.
Они привязаны к действующим стендам. Для создания отдельного экземпляра шаблон
portable v1 регистрируется через `POST /projects/{code}/stand-templates`.

## Проверка и создание

Тело обоих запросов одинаковое:

```json
{
  "name": "Проверка feature",
  "template_key": "template-demo",
  "template_version": "1.0.0",
  "target_host": "laptop",
  "profile": "laptop",
  "components": {"api": {"repository": "demo", "ref": "feature/orders"}},
  "parameters": {},
  "environments": ["feature-orders"],
  "mode": "permanent",
  "expires": null,
  "ports": {}
}
```

Неуказанные component refs и параметры берутся из шаблона. При неоднозначном
коротком имени ветки/тега используйте `refs/heads/...` или `refs/tags/...`.
Для временного экземпляра задайте `mode: "ephemeral"` и будущий `expires` с поясом,
например `2026-12-01T18:00:00+03:00` (актуальную дату выбирает пользователь).
Стенд доступен по эту дату включительно. В примере срок заканчивается в полночь
2 декабря по `+03:00`. Для существующих записей без исходного смещения используется
дата сохраненного времени UTC. Разработчик может создавать только временные экземпляры.

`ports: {}` выбирает свободные порты пула. Явный выбор задаётся по output binding,
например `{"baseUrl": 20001}`. Алиасы одного service/port обязаны использовать
один host port. Проверяется реестр резерваций; доступность порта в ОС проверит
исполнитель. Уже занятое окружение проекта нельзя переназначить новому стенду.

Preflight возвращает `observed_sha` по компонентам, лимиты профиля и предварительные
порты. Эти результаты не бронируют ресурсы и не фиксируют окончательный SHA сборки.
`executor_available` показывает наличие недавнего опроса активного агента,
привязанного к хосту. Это не резервирование исполнителя на момент будущего создания.

Создание требует пользовательской cookie-сессии; API-токен не задаёт владельца.
Отправьте постоянный для одной операции ключ, например `Idempotency-Key: demo-create-001`.
Успех — 201; повтор того же нормализованного тела тем же владельцем — 200 с теми же
ID стенда/задания и портами. Другой запрос с тем же ключом — 409. После сетевого сбоя
повторяйте исходный ключ и тело, чтобы не создать второй экземпляр.

Отмена через `POST /api/jobs/{job_id}/cancel` отменяет ожидающую сборку, но сохраняет
экземпляр и портовые резервации. JSON snapshot, параметры и команды не предназначены
для значений секретов.

## Удаление

Портал раз в минуту проверяет срок временных управляемых стендов. После окончания
дня и освобождения стенда от задач портал ставит обычное задание `stand-delete`.
Задание в очереди дождется агента, привязанного к хосту. Истекшие во время простоя
сроки обрабатываются после запуска портала. При ошибке или отмене автоматической
попытки можно повторить удаление из карточки или через
`DELETE /api/projects/{code}/stand-instances/{instance_id}`.

Агент подтверждает очистку ресурсов. После подтверждения портал освобождает порты
и убирает стенд из рабочего списка. Карточка, история сборок и отчеты доступны по прежним адресам.

Повтор по сохранённым SHA и история сборок описаны в [протоколе агента](local-stand-agent.md).
Он требует уже сохранённый snapshot; ошибка подготовки до snapshot не выдаётся
за воспроизводимый повтор сборки.
