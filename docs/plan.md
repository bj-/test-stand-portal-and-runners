# План переносимой поставки

2026-11-18. План поставки; мастер создания стендов реализован в отдельном портале.
Полная приёмка всех этапов ещё не завершена.

## Целевой сценарий

Пользователь выбирает проект, создаёт стенд из готового шаблона, выбирает ветку
каждого компонента и запускает сборку и тесты. Тот же шаблон работает на общем
сервере и локально. Сборка фиксирует фактические commit SHA; результаты остаются
доступны после перезапуска.

## Порядок работ

| Этап | Результат | Приёмка |
|---|---|---|
| 0 | Установщики зависимостей Windows/Ubuntu/macOS | Пользователь с чистой машиной проходит установку по инструкции без LLM, повтор после reboot сохраняет состояние |
| 1 | Изолированный локальный портал и нейтральный HTTP-пример | Повтор init сохраняет пароль и данные; независимые установки; smoke возвращает ненулевой код при ошибке |
| 2 | Контракт шаблона: компоненты, репозитории, миграции, healthcheck, ресурсы | Один реальный шаблон полностью работает через CLI без изменения исходных clones |
| 3 | Сборка из веток/коммитов, снимок состава | Несуществующая ветка даёт ошибку; повтор по SHA воспроизводит состав; разные ветки компонентов не смешиваются |
| 4 | Каталог проектов и экземпляров в портале, мастер создания | Создание, сборка и запуск тестов без редактирования YAML; права и конфликты ресурсов проверены |
| 5 | Локальный агент и сохранение результатов | Реальный прогон через портал, логи, результаты и Allure; локальный режим не требует push результатов |
| 6 | Временные стенды и ресурсные ограничения | Владелец, квоты, срок жизни, остановка и продление; удаление не затрагивает соседние данные |
| 7 | Контейнерная приёмка на Windows, Ubuntu, macOS | Развёртывание с нуля, перезапуск, два стенда, проверка arm64/amd64 и сохранения результатов |

Необходимость шаблона принципиальна: выбор Git-репозитория не сообщает автоматически
способ сборки, зависимости, миграции и порты приложения. Сначала поддерживается
один законченный сценарий, затем дополнительные типы сервисов и runners.

### Первый шаг к этапам 2–3, 2026-11-18

В [stands/](../stands/README.md) добавлены контракт JSON v1, `validate`, `prepare`
и `replay`: компоненты и зависимости, профили ресурсов, Compose/lifecycle,
ссылки на секреты и привязки окружения; точное разрешение локальных refs,
полные SHA, frozen template и экспорт в отдельные каталоги без изменения clones.

Этот первый шаг подготовил исходники; ранний JSON служит примером контракта.

### Исполнение и скрипт развёртывания, 2026-11-18

[deploy.ps1 / deploy.sh](../DEPLOY.md) объединяют установку портала и запуск
учебного template-demo. Executor выполняет Compose lifecycle, сохраняет
стадии/логи/SHA/image IDs/digests/baseUrl, разделяет результаты попыток,
поддерживает явный retry и stop с сохранением данных. Пример содержит SQLite,
миграцию, засев, healthcheck и smoke с Allure. Ветки API и runner выбираются отдельно.

71 тест и 193 подпроверки прошли после исправления закрытия SQLite connections;
Compose 2.39.4 проверил реальную модель и override без daemon. Пользователь
2026-11-18 сообщил, что сам запустит готовый скрипт: фактический Docker запуск
и приёмка ОС на тот момент ожидались. Затем Windows Docker lifecycle принят: успех,
ошибка smoke и retry с сохранением БД. Очередь, host-worker и мастер UI портала
подключены; worker поддерживает явный fetch, а CLI подготовки читает локальные refs.
Продуктовый адаптер и приёмка чистых установок трёх ОС ещё нужны; этапы 2–3
целиком не объявляются закрытыми. Владелец разрешил публикацию переносимого кода.

## Разделение компонентов

- Переносимый код и нейтральные примеры — здесь.
- Код портала — отдельный проект `test-portal`, с собственной лицензией и доступом.
- Адреса, список частных репозиториев, секреты, сертификаты, данные и результаты —
  в каталоге установки снаружи checkout.
- История существующих частных установок не импортируется в публичный репозиторий.

## Улучшения сценария

Клонирование настроек стенда; предварительная проверка refs, портов и агента;
раздельные действия «повторить прежнюю сборку» и «обновить из веток»; минимальный
профиль для ноутбука; остановка по сроку с отдельным удалением данных.

## Технические опоры

Compose позволяет разделять установки именем проекта
([документация](https://docs.docker.com/compose/how-tos/project-name/)).
Для Windows/macOS Compose входит в Docker Desktop; варианты установки для Ubuntu
описаны в [инструкции Docker](https://docs.docker.com/compose/install).
Поддержка Apple Silicon проверяется отдельно для образов `linux/arm64`;
эмуляция не заменяет нативную приёмку
([multi-platform builds](https://docs.docker.com/build/building/multi-platform/)).
