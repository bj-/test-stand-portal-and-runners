# Обновление портала на Linux

`run.py` — независимый процесс Python 3 без внешних Python-зависимостей. Git и
доверенный адаптер установки должны присутствовать на хосте. Процесс проверяет
один настроенный репозиторий и полную ссылку ветки/тега после готовности портала
при запуске и затем раз в 3600 секунд по монотонным часам. Сервис запускается
независимо от портала: ожидание готовности и отсутствие сети не задерживают запуск
уже установленного приложения. Запросы администратора обрабатываются между
проверками. Настройки и установка systemd находятся в репозитории test-stands.

```bash
python3 /opt/test-portal-updater/run.py --config /etc/test-portal-updater.json
python3 /opt/test-portal-updater/run.py --config /etc/test-portal-updater.json --once
```

`--once` выполняет один проход: сначала накопленный ручной запрос либо проверку
после готовности портала. Если портал ещё не готов, процесс завершается без
проверки; постоянный сервис повторяет проверку готовности через `poll_seconds`.
Результат операции записывается в JSON; код выхода `--once` отражает запуск самого
процесса, а не результат обновления.

## Настройки и права

Пример — [config.example.json](config.example.json). `repository`, `state_dir`,
`work_dir` и `adapter` обязательны. Остальные значения показаны в примере вместе
со значениями по умолчанию. `adapter` — массив аргументов с абсолютным путём
исполняемого файла первым элементом; shell не используется. `auto_apply` управляет
применением по расписанию. Ручной `check` только проверяет; ручной `apply` проверяет
и применяет независимо от `auto_apply`.

Конфигурация, исполняемый код, адаптер и `work_dir` контролируются администратором
хоста. Портал получает доступ только к `state_dir` и не может менять Git-адрес,
ref, адаптер, команды или рабочие файлы. `state_dir` содержит общедоступные для
администраторов портала состояния и очередь, `work_dir/worker.json` — закрытую
внутреннюю блокировку восстановления и последнюю неудачную ревизию. Рабочий каталог
и исходники releases имеют права 0755 для чтения локальными исполнителями;
внутренний JSON создаётся с 0600. Права общей очереди и группы задаёт установка.
Общие status/operation JSON также имеют 0600: текущая установка запускает портал
и updater от root. При переходе портала на другого пользователя установщик должен
согласовать доступ к очереди и состояниям, сохранив work_dir под контролем хоста.

URL не должен содержать токены, пароль, query или fragment. Для HTTPS также
запрещено имя пользователя в URL. Используются credentials окружения/credential
helper и SSH-конфигурация хоста; интерактивные Git-подсказки отключены. Окружение,
вывод Git и адаптера и тексты исключений не попадают в публичные состояния или
логи процесса. Для диагностики хоста адаптер может вести собственный защищённый
журнал. Таймаут убивает всю Linux-группу дочернего процесса.

## Очередь и состояния

Портал атомарно создаёт `state_dir/requests/<uuid>.json`:

```json
{"id":"18feff9e-8414-4f00-acb9-e80d60142ca5","action":"apply","requested_by":"admin","created_at":"2026-11-18T12:00:00+00:00"}
```

Поддерживаются только `check` и `apply`. Файлы запросов сохраняются; наличие
`operations/<uuid>.json` предотвращает повторное выполнение. Запросы `check`
объединяются с текущей операцией, а `apply` — с текущим применением. Для каждого
запроса создаётся отдельный результат с тем же итогом. `apply`, пришедший во время
ручного `check`, остаётся в очереди до следующего прохода.

Операция содержит только `id`, `action`, `requested_by`, `created_at`,
`started_at`, `finished_at` (для завершённой операции), `phase`, `message`,
`current_revision`, `available_revision`. `status.json` содержит только `enabled`,
`current_revision`, `available_revision`, `last_checked_at`, `phase`, `message`,
`last_operation_id`, `updated_at`. При ошибке дополнительно присутствуют
`failure_phase` (исходный этап ошибки до rollback) и `error_code`
(`command_timeout` или `update_failed`). При новой неблокированной операции эти
поля очищаются. Времена имеют формат ISO 8601 UTC; неизвестная
ревизия — пустая строка. Тексты состояний фиксированы и не содержат командного
вывода. Записи выполняются через временный файл, fsync и атомарный rename.

Рабочие фазы: `checking`, `preparing`, `draining`, `backing_up`, `activating`,
`verifying`, `resuming`, `rolling_back`. Завершение: `unchanged`, `available`,
`succeeded`, `failed`, `recovery_required`. `idle` используется только для общего
состояния готового процесса. Одновременно может работать только один процесс:
Linux `flock` на `state_dir/worker.lock`.

## Протокол адаптера и безопасность применения

Все команды вызываются как `adapter + [command, ...args]`. Нулевой код выхода
обозначает успех. Команды с JSON должны вывести только один объект, до 64 КиБ.

| Команда | Аргументы | stdout / действие |
| --- | --- | --- |
| `current` | — | `{"revision":"<40 hex или пустая строка>"}` |
| `prepare` | source_path, sha | Собрать кандидата без остановки текущего портала |
| `drain` | — | Включить maintenance, затем `{"running":N,"maintenance":true}` |
| `idle` | — | `{"running":N,"maintenance":true}` |
| `backup` | operation_id | `{"backup":"<непустой путь>"}` после успешной копии БД |
| `activate` | source_path, sha | Остановить исполнителей, применить готовый образ/миграции |
| `health` | — | Дождаться готовности с ограниченным временем; exit 0 при готовности |
| `resume` | — | Запустить исполнителей и открыть приём новых прогонов |
| `rollback` | — | Вернуть приложение только при совместимой схеме БД; иначе ошибка |

Адаптер самостоятельно хранит метаданные резервной копии, старого образа и схемы;
`activate` должен отказать без подтверждённой копии БД. Только адаптер управляет
maintenance. Worker не восстанавливает БД автоматически.

Git fetch выполняется в отдельный bare-репозиторий `work_dir/repository.git`.
Полученный commit SHA фиксируется один раз; `git archive` экспортирует его в
`work_dir/releases/<sha>`. Символические и жёсткие ссылки, специальные файлы и
небезопасные пути отклоняются. Checkout, Git hooks и изменение установленного
репозитория не используются. Успешная сборка помечается файлом `<sha>.prepared.json`
и повторно не запускается для этой ревизии. При ошибке применения метка удаляется:
явный повторный apply пересобирает образы, в том числе после Docker prune.
Релизы и резервные копии сохраняются;
автоматической очистки нет.

Порядок применения: prepare → drain → idle до нуля активных прогонов → backup →
activate → health → resume. Ошибка до активации оставляет старое приложение и
при необходимости выполняет health/resume. Ошибка активации или проверки здоровья
вызывает rollback, затем health/resume только при успешном безопасном возврате.
Ошибка самого resume требует ручной проверки без rollback: приём прогонов уже
мог открыться и новые задания могли начаться.
Отказ rollback оставляет `recovery_required`. Повторная автоматическая попытка
неудачной ревизии блокируется до явного ручного `apply`; ручной `apply` также
блокируется при `recovery_required`.

## Прерывание и восстановление

После прерывания на drain/backup процесс проверяет старое приложение и вызывает
resume. Прерывание activate/health/rollback/resume переводит установку в
`recovery_required` без автоматического открытия приёма. Блокировка сохраняется
в защищённом `work_dir/worker.json`; последующие ручные проверки источника и
перезапуски процесса её не снимают.

После ручной проверки и исправления приложения/схемы администратор останавливает
сервис updater и выполняет:

```bash
python3 /opt/test-portal-updater/run.py --config /etc/test-portal-updater.json --acknowledge-recovery
```

Команда проверяет health, валидность установленной ревизии, выполняет resume и
только затем снимает внутреннюю блокировку. После этого можно запускать сервис.
Она не меняет БД и не выполняет rollback.

Адаптер может атомарно установить новую версию самого `run.py` при успешном
resume. После завершённого `succeeded`/`unchanged` постоянный процесс сравнивает
SHA256 своего файла с исходной версией и выполняет exec Python с прежними
аргументами. Дескриптор flock закрывается при exec; новый процесс проходит обычную
проверку состояния. `--once` сам себя не перезапускает.

## Проверка

```bash
python3 -m unittest discover -s updater -p test_updater.py -v
```

Тесты используют настоящий локальный Git и поддельный адаптер. Проверяют порядок
обновления, offline/build/backup/drain ошибки, безопасный rollback, запрет
автоматического восстановления несовместимой схемы, перезапуск после прерывания,
объединение запросов, расписание, ограничение времени и экспорт без symlink.
Проверки flock и Unix-прав требуют Linux.
